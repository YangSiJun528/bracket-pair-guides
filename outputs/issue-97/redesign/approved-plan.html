01 · Architecture

컴파일 의존성은 다섯 모듈로 제한한다

실선은 소스의 컴파일 의존 방향이다. 실행 중 UI→runtime 호출은 UI가 소유한 interface를 통해 일어나므로 컴파일 의존 순환을 만들지 않는다. model은 필요한 계약에 따라 전이 노출될 수 있다.

모듈외부에 보이는 interface숨기는 implementation의존 설정
analysis-modelBracketView, TokenWindow, Pair/Guide/Range, facets·결과 상태배열, builder, source stamp, Editor는 없음프로젝트 의존 없음
analysis-coreBracketCalculator의 analyze/repair, 입력·제어 interface와 불변 입력 값pairing, 규칙 캐시, 정렬, indexes, guide builder, 재사용api(model)
editor-uiEditorGuides bootstrap, GuideWork/Factory, GuideView와 요청 값표시 정책, markers, markup, guideRevision, 설정·안내 상태api(model) + SDK
analysis-runtimeRuntimeGuideWorkFactory: UI 계약만 반환source stamp, read capture, Jobs, lane tickets, accepted cache, native proofapi(editor-ui), implementation(core) + SDK
pluginIntelliJ extension adapter·등록연결 코드만; 계산·표시 정책 없음implementation(UI/runtime); core 금지
runtime factory의 반환형이 UI 계약이므로 UI 의존은 api로 노출할 수 있다. core 의존은 반드시 implementation으로 둔다. 실제 Kotlin·Java 컴파일 입력에서 이 효과를 다시 증명한다. Gradle java-library의 api/implementation 계약

물리 격리와 세부 구현 숨김은 서로 다른 검증이다

UI→core/runtime, plugin→core는 classpath 부재로 막는다. runtime이 core 내부 구현을 Java로 우회하는 문제는 private/package-private 및 새 ArchUnit 규칙으로 보완한다. Kotlin internal만으로 Java 접근이 막힌다고 보지 않는다. 최종 플러그인에는 실행에 필요한 5개 모듈이 함께 들어가므로, 이것을 reflection까지 막는 보안 sandbox라고 표현하지 않는다.

02 · Code-level design

interface는 호출자가 해야 할 일을 기준으로 만든다

아래 이름과 형태는 구현 초안이다. 메서드 수를 줄이는 것보다, 호출자가 알아야 하는 진행 순서·수명·실패 처리의 양을 줄이는 데 초점을 둔다. 모든 클래스에 interface/Default 구현 쌍을 만들지는 않는다.

A. 읽기 전용 결과 — analysis-model

interface BracketView {
    fun activePairAt(offset: Int): BracketPair?
    fun guideFor(pair: BracketPair): BracketGuide?
    fun visibleTokens(range: OffsetRange, focus: Int, maximum: Int): TokenWindow
}
// TokenWindow는 bounded indexed read-only 계약이다.
// backing array / index / builder / lazy IntelliJ 객체는 반환하지 않는다.
// BracketPair · BracketGuide · OffsetRange는 불변 값이다.

abstract snapshot에 host stamp를 상속시키지 않는다. runtime의 AcceptedAnalysis(sourceStamp, result)가 유효성을 소유하고, UI에는 승인된 결과 조회만 제공한다. 의미 있는 작은 내부 memo는 가능하지만 결과 의미와 동시 사용 계약을 바꾸지 않아야 한다.

B. 계산 use case — analysis-core

// public final class. 이 두 메서드가 runtime이 배우는 계산 interface다.
class BracketCalculator {
    suspend fun analyze(
        input: BracketInput,
        facets: AnalysisFacets,
        control: CalculationControl,
    ): CalculatedBrackets = /* internal attempt가 전체 계산을 수행 */

    suspend fun repair(
        input: LineInput,
        target: RepairGeometry,
        control: CalculationControl,
    ): BracketGuide? = /* 내부 예산과 후보 선택을 적용 */
}

interface BracketInput : LineInput {
    suspend fun tokensAt(offset: Int): TokenBatch
    suspend fun areCompatible(open: TokenKind, close: TokenKind, group: TokenGroup): Boolean
}
interface LineInput {
    suspend fun beginAttempt(): DocumentFacts
    suspend fun initialPrefixes(firstLine: Int, lineCount: Int): PrefixBatch
    suspend fun continuePrefix(line: Int, afterOffset: Int): PrefixChunk
    suspend fun validateCurrent()
}
interface CalculationControl {
    fun checkCanceled()
    suspend fun yieldWork()
}

입력 interface는 core가 소유하고 runtime의 IntelliJ adapter가 구현한다. adapter는 실제 readAction 안에서 불변 청크만 만든다. core 내부의 pairing·정렬·indentation 계산은 read access 없이 진행한다. suspend 자체에 IntelliJ나 kotlinx.coroutines 의존은 필요 없으며, runtime이 기존 Job/ProgressManager를 control에 연결한다.

호출자가 알아야 하는 계약호출자가 몰라도 되는 구현
정확한 offset에서 다음 청크를 얻고, 진전 또는 end를 보장한다. 청크는 봉인 후 불변이다.PairingMachine.Step, RuleRequest cache, PairCollection, sort strategy
source 변경은 stale로 종료한다. unrelated write의 capture retry만 새 attempt로 재시도한다. 취소는 정상 결과로 바꾸지 않는다.prepare → guideLines → builder → seal → finish 순서와 중간 저장소
analyze는 필요한 facet의 결과 또는 의미 있는 제한 결과를 돌려준다. repair 거절은 숨겨진 guide를 되살리지 않는다.PairTable, IndexLayout, ActiveIndex, GuidePositionIndex, 내부 weak cache
입력 값 생성용 bounded collector/factory가 필요하면 core/input에만 둔다. TokenBatch.begin(PairingMachine.Session)처럼 DTO가 알고리즘을 노출하게 만들지 않는다. UI는 입력 생성 계약 자체를 컴파일할 수 없다.

C. 작업과 표시 — editor-ui가 소유하는 interface

interface GuideWorkFactory {
    fun attach(editor: Editor, view: GuideView): GuideWork // EDT, editor당 한 번
}
interface GuideWork : AutoCloseable {
    fun reconcile(demand: GuideDemand) // EDT: 원하는 현재 상태를 한 번에 전달
    fun refresh()                     // any-thread: 최신 demand의 비동기 wake-up
    fun observeNativeGuide(candidate: DisplayedGuide) // paint에서는 값 비교만
    override fun close()              // any-thread, idempotent, 즉시 ticket 폐기
}
interface GuideView {
    fun applyAnalysis(update: AnalysisUpdate): ViewApplication // EDT, non-suspending
    fun applyRepair(update: RepairUpdate): ViewApplication
    fun reportNativeConflict(evidence: NativeConflictEvidence)
}
// GuideDemand: facets/options/visibility + typed change cause
//            + demandRevision + guideRevision + RepairIntent? + native interest
// repair=null은 현재 repair target 없음/취소라는 완전한 상태다.
// 전달 값에 source stamp, Job, builder, 구체 index는 없다.
// ViewApplication = APPLIED / OBSOLETE

reconcile 내부에서 이전 작업 무효화→새 demand 설치→repair/full scheduling을 처리한다. UI는 update → cancel → repair → refresh의 순서를 알 필요가 없다. caret/viewport만 바뀌면 현재 결과를 조회하고 전체 분석을 다시 만들지 않는다. 재전달된 동일 demand는 중복 작업을 만들지 않는다.

세 작업의 취소 세대는 분리

source edit는 세 작업을 모두 무효화한다. full 분석의 최신 결과가 도착하면 해당 repair를 폐기한다. caret 이동은 repair/native 대상만 바꾸며 유효한 full 계산까지 무조건 취소하지 않는다. source epoch와 표시 revision을 같은 숫자로 취급하지 않는다.

반영은 EDT 계약으로 검증

UI 반영은 suspend하지 않는다. SDK callback 재진입 시 revision을 다시 확인하고, 실패한 임시 markup은 폐기한다. 반영 뒤에도 runtime fence를 재검사하고 좁은 lock/CAS로 close와 승인 commit의 경쟁을 막는다. lock 안에서 SDK 호출은 하지 않는다.

markup과 accepted cache가 모든 스레드에서 동시에 바뀌는 전역 transaction이라는 뜻은 아니다. 실패·OBSOLETE는 completed 상태로 기록하지 않는다. edit 처리 실패도 작업 무효화를 누락하지 않도록 finally/종료 경로를 검증한다.

동일 문서의 저장소 재사용

runtime의 문서 수명 registry가 단조 증가 ReuseRevision을 발급한다. core는 revision·내부 layout·필요한 tabSize와 정확한 내용 비교로 불변 저장소를 재사용한다. source stamp와 IntelliJ 객체는 전달하지 않는다. 늦게 끝난 옛 revision은 현재 cache generation을 되돌릴 수 없다. split editor의 query memo와 표시 상태는 각각 소유한다.

06 · Use existing tools

도구는 재사용하고, 자체 구현은 필요한 정책만 남긴다

선택용도 / 조건
JUnit + AssertJ 유지새 순수/정책 테스트는 기존 Jupiter를 사용할 수 있다. IntelliJ fixture는 최소 지원 IDE에서 검증된 Platform/JUnit4 실행과 분리한다. framework 이식 자체를 목표로 삼지 않는다.
Gradle TestKit 사용별도 임시 프로젝트에서 실제 빌드와 compiler를 실행한다. 자체 Python compiler launcher를 대체한다. 공식 TestKit 문서
기존 ArchUnit 소규모 사용새 규칙: runtime은 ui/work 계약만 사용, 외부에서 core/internal 참조 금지. ui/presentation/policy는 SDK 금지, editor-ui 전체는 Job 소유 금지. Editor를 받는 work/bootstrap·IntelliJ adapter는 SDK 허용. 실제 참조 검사이므로 classpath audit를 대신하지 않는다. ArchUnit 분석 범위
Spotless + Qodana 유지formatter와 정적 검사. 기존 zero-problem gate 유지; 새 코드·테스트·build-logic를 baseline/제외로 숨기지 않는다. Qodana quality gate
JMH + GC profiler 유지새 public 계산/조회 workload의 ns/op·B/op. 측정 자체를 새로 구현하지 않는다. JMH 공식 프로젝트
IntelliJ Test/Verifier/Driver 유지공식 testIde의 target·sandbox 기능, plugin structure/configuration/compatibility 검사, 실제 UI 실행을 사용한다. 공식 testing extension

새 도구 기본 추가 없음DI framework, EventBus, generic workflow engine, 자체 test runner, Kotest/jqwik/PIT/새 린터는 현재 필수 요구가 없다.

일반 도구가 대신해 주지 않는 최소 구현

  1. 컴파일 입력 정책 task: 허용 project graph뿐 아니라 실제 Kotlin/Java classpath·source·output·friend·sourcepath/processor/compiler 입력을 점검한다. JAR 이름이 달라도 금지 owner class가 섞이면 거절한다.
  2. 최종 ZIP 소유권 task: 각 production class의 중복·누락·test/SDK 혼입과 필수 자원을 확인한다. byte 비교 기준은 실제 패키징에 사용한 owner 산출물이며, instrumentation이 있으면 raw compile bytes와 혼동하지 않는다.
  3. IDE 도메인 계측 adapter: writer 대기·read 구간·취소·payload 수명 측정만 담당한다. 범용 scheduler/reporter를 다시 만들지 않는다.

접근 제한은 우회 원인별로 확인

존재·가시성이 확인된 core 진입점과 runtime 입력/실행 심벌은 owner에서 Kotlin/Java 긍정 대조를 먼저 실행한다. 같은 심벌의 UI 참조, plugin의 core 참조는 실제 compiler에서 실패해야 한다. 완전 private 자료구조는 공개 노출·소유권 검사로 확인한다. 사라진 이름을 참조해서 실패한 것을 격리 증거로 세지 않는다.

unused 직접 의존, 전이 api 노출, 공유 source/output, 금지 class를 복사한 JAR, source-only archive, javac sourcepath/bootstrap/processor 및 Kotlin friend/classpath 입력 변경을 각각 주입한다. 원인에 맞는 정책 실패와 원상 복구 후 성공을 확인하며 cold clean과 warm 실행을 모두 남긴다.

TestKit은 실제 체크아웃의 빌드 설정을 사용해야 한다. 단순 Java 예제 프로젝트만 통과시키면 이 저장소의 Kotlin compile 입력을 입증하지 못한다. 임의의 악성 Gradle plugin까지 봉쇄하는 sandbox를 만드는 것은 범위가 아니다.

SDK 없는 실행을 독립 진입점으로 강화

tools/pure-build/settings.gradle.kts에서 model/core의 실제 source와 build 설정만 포함하고, SDK 설정 plugin 없이 빌드한다. main 빌드와 output·project cache를 분리한다. 새 production 모듈은 늘지 않는다. 기존 -PpureBuild가 SDK bytecode만 제외하고 IntelliJ Gradle settings tooling은 읽는 점을 개선한다.

# 제안 명령. 아직 구현/실행된 task가 아니다.
./gradlew -p tools/pure-build :analysis-model:build :analysis-core:build
./gradlew spotlessCheck check
./gradlew :plugin:buildPlugin :plugin:verifyPluginStructure :plugin:verifyPlugin
# IDE별 test/Driver task 이름은 pinned Gradle plugin으로 working slice에서 확정한다.

Gradle 실행 JDK, Java17 compile toolchain, 테스트 JVM, 실제 IDE JBR을 구분해 기록한다. 최소 IDE의 fixture를 검증 없이 최신 JUnit engine으로 일괄 교체하지 않는다.

07 · Performance & real IDE evidence

재설계의 추가 비용을 같은 조건에서 비교한다

기준: 072533f후보: 재설계 완료 commit새 JVM · AB/BA 균형 순서기본 5개 독립 pairlatency + allocation + writer + lifetime
  1. 측정 전에 의미를 고정한다. 입력 seed·크기·facets·결과 소비·warmup/fork·JDK/IDE/heap/GC·primary metric과 판정 기준을 적는다. 새 interface와 과거 구현의 동일 작업량을 맞추는 baseline 전용 adapter는 비교용 worktree에만 둔다.
  2. 새 JMH workload를 만든다. 보통/희소/고밀도/깊은 중첩/비정상 입력의 analyze, repair, query를 측정한다. 내부 private 함수 접근을 유지하려고 public surface를 넓히지 않는다.
  3. 실제 IDE에서도 측정한다. read 점유, writer 대기, 취소 지연, 전체 분석, 숨김→유효 repair, native proof, 보유 payload를 확인한다. 단위 테스트 시간은 UI 응답성 증거가 아니다.
  4. 실패 자료까지 보존한다. pair별 ratio와 원시 표본·표본 수를 보고한다. 불명확하면 사전에 정한 추가 pair만 실행하며 유리한 결과까지 반복하지 않는다. 다른 빌드/Driver/Verifier/Qodana와 성능 측정을 병렬 실행하지 않는다.
  5. 기준을 약화하지 않는다. 기존 benchmark gate의 20% 및 job 240초 기준과 자원 한계는 완화하지 않는다. 새 workload의 의미가 달라 직접 비교할 수 없으면 비교 불가로 표시하고 대체 증거를 만든다. 이력 gate 하나로 성능 동등성을 선언하지 않는다.
과거 위험은 해결된 것으로 간주하지 않는다. 이전 이슈 #97 증거에는 writer p95 약 +20%, repair worker p95 +29.4%, 소량의 allocation 증가와 양쪽 revision의 XML classifier 잔존이 있다. 이번 설계가 이를 해결한다는 증거는 없다. 072533f와의 추가 회귀 비교와 PR #96 대비 과거 문제 추적을 분리한다. 기존 검증의 해석 한계

실제 IDE·시각·패키징

현재 지원 범위를 기본으로 유지한다. 최소 IDE와 현재 선택 IDE에서는 새 실제 fixture를 실행하고, 현재 13개로 해석된 지원 IDE matrix에는 동일 ZIP SHA로 Plugin Verifier를 실행한다. target 목록은 실행 시 다시 고정한다. Driver는 고정 OS/DPI/font/theme/JBR에서 대표 geometry, edit 후 hide/repair, disable·native 복원부터 작성하되 기존 사용자 동작 범위에 누락이 없게 시나리오 표로 추적한다. 단위 테스트로 확인할 수 없는 동작은 모두 작은 실제 실행 검증에 남긴다.

기존 PNG는 삭제하지만, 새 기대 화면은 사용자 동작에서 도출해 검토한다. 변화가 발견되면 의도한 변경인지 확인하고, 후보 출력을 그대로 녹화해 통과시키지 않는다. Verifier 성공·Driver 성공·성능 성공은 서로 대체되지 않는다.

08 · Implementation plan

계약을 정한 뒤 작은 실제 흐름부터 완성한다

하위 호환 facade와 기존 테스트 포팅은 만들지 않는다. 단계별 로컬 commit으로 되돌릴 수 있게 하고, 통합 전까지 원본 작업과 기준 revision을 보존한다. 새 구현용 worktree는 실행을 시작할 때 별도로 준비한다.

0 · 설계 고정

책임·삭제 범위·측정 기준 확정

GLOSSARY, module README 형식, ADR 연결, 새 계약 matrix, 기존 테스트/도구 삭제 목록, 동조건 baseline 입력을 고정한다. 공개 이름보다 소유권과 실패 의미를 먼저 확정한다.

기존 테스트 삭제와 새 빌드 계약

기존 테스트 자산 전부를 삭제하는 commit을 남기고, TestKit·SDK-free 진입점·새 소유 모듈 테스트 skeleton을 추가한다. 빈 suite로 전체 check가 녹색이 되지 않게 필수 계약 suite를 연결한다. API 접근 실패와 긍정 대조를 먼저 red/green으로 만든다.

BracketView와 값 계약을 확정하고 작은 core 테스트부터 analyze/repair를 구현한다. runtime에 있던 pairing/guide 조립 반복문과 내부 재사용을 core로 옮긴다. DTO는 bounded primitive storage를 유지한다.

단계 종료 조건 · 새 순수 계약 테스트; SDK 없는 build/test; 계산 단계의 public protocol 제거.

단계 종료 조건 · 실제 worker/read/EDT 증거와 최소 plugin smoke; runtime factory에 core 타입 노출 없음.
4 · UI/runtime

수명·승인·표시를 재작성

full/repair/native ticket과 accepted/refusal을 runtime에 통합한다. UI는 표시와 동기 hide를 맡는다. reconcile로 실행 순서를 숨기고 stale·dispose·재진입·render 실패를 새 테스트로 검증한다.

단계 종료 조건 · ADR 0001/0002의 새 테스트, 지연 repair 거절, close 경쟁, 중복 registry 제거.

native 안내·설정·시각 기준

단계 종료 조건 · 새 사용자 동작 검증, UI 수명 누수 없음, 최종 ZIP class/resource 검사.

린트·전체 IDE·동조건 성능

표준 CI task로 통합하고 자체 runner/reporter를 제거한다. old→new 검증 목적 누락을 점검한다. 최종 ZIP 하나로 호환성·실제 실행을 확인하고 직렬 성능 비교를 수행한다.

단계 종료 조건 · 미실행·불확실·회귀는 분리 보고. 기준을 낮춘 pass는 없음.

09 · Definition of done

완료는 코드 모양이 아니라 증거로 판단한다

조건필요한 증거
호출자가 내부 구현을 모른다UI→core/runtime, plugin→core의 실제 Kotlin/Java 컴파일 실패. runtime은 core public 계산/input 계약만 사용.
순수 계산을 독립적으로 개발할 수 있다SDK 없는 model/core clean build와 새 계산 테스트; IntelliJ 객체·lazy PSI·read가 필요한 결과 getter 없음.
상태 소유권이 명확하다accepted/source/job은 runtime, markup/guideRevision은 UI. 새 stale·cancel·close·재진입 계약 테스트.
기존 실행·표시 결정이 유지된다실제 read/worker/EDT, 동기 hide, 즉시 repair, 새 Driver 증거.
테스트 전면 교체가 끝났다기존 테스트/fixture/helper/baseline/friend 경로 없음. 새 suite가 핵심 계약 표를 충족하며 NO-SOURCE는 제외.
기존 도구로 검증이 이어진다Spotless/Qodana/check, 실제 TestKit 우회 주입, SDK fixtures, Driver, JMH, Verifier 실행 기록.
같은 플러그인을 검증했다최종 ZIP SHA, 5모듈 owner class·resource·runtime dependency 검사와 지원 IDE 실행·검증 로그.
추가 비용이 숨겨지지 않았다동조건 baseline/candidate raw 자료, latency/B/op/writer/lifetime 비교와 미해결 신호.

단위 테스트는 구조를 검증하는 도구이지만 실제 IntelliJ 스레드·read·등록 계약을 모두 대체하지 못한다. 따라서 새 단위 테스트를 중심에 두되 최소한의 새 IDE 통합·Driver·성능 검증을 함께 설계했다. 구조적 격리가 모든 알고리즘·동시성 버그의 부재를 뜻하지는 않는다.

구현에서 확인할 항목

  • pinned IntelliJ Gradle plugin에서 모듈별 새 test task를 구성하는 정확한 방식. 필요하면 plugin에 실행 task만 두고 테스트 소유권은 해당 모듈에 유지한다.
  • 새 input facts와 suspend orchestration이 allocation·취소 빈도에 미치는 비용.
  • per-document canonical reuse의 weak lifetime과 stale completion 처리.
  • 최소 IDE의 test engine 호환성과 새 Driver baseline의 기대 동작.

Top recommendation

첫 번째 구현 대상은 계산 시도 소유권의 이동이다

core가 analyze/repair를 완결하면 runtime의 알고리즘 지식을 없애고 새 단위 테스트를 한 interface에 집중할 수 있다. 계산 deep module 전후 비교로 이동

이번 산출물은 계획과 시각 보고서다. 저장소의 프로덕션·테스트·빌드 설정은 수정하지 않았고, 새 테스트·성능 측정·커밋을 실행하지 않았다. 외부 제출·업로드도 하지 않았다. 로컬 파일 링크와 문서 내 anchor는 검사했으며, 브라우저의 file:// 정책 차단으로 화면 렌더링은 검증하지 못했다.
적용: improve-codebase-architecture + codebase-design. 사용자가 전면 재설계와 구체 interface 계획을 이미 요청했으므로 후보 선택을 다시 요구하지 않고 통합 계획까지 작성했다.
