# Focused source diagnosis of repeated fixture signals

Baseline `84d1a43141b1933c81e027ef01d1579fc4679e6e`; measured candidate `f7599fa39be7d8e93cc339da719b14012ab1a1dd`. Read-only comparison of a few relevant files; no build, workload, profile, bytecode scan or production edit. This diagnosis supplements `independent-current-review.md`; it does not invalidate its observed timing/allocation increases.

## Proven source facts

`GuideRepairExecution`, `BracketAnalysis`, `AnalysisReadEpoch` and `DocumentTextCapture` are source-identical after relocation. `GuideRepairCalculation` changes its class visibility from internal to public; its scan order, budgets, iterator, result construction and cancellation callback body are unchanged. `BracketModels` changes class visibility. These facts exclude an explicitly added algorithm step in those bodies, but do not imply equal generated bytecode, JIT inlining, allocation elimination, linkage or runtime scheduling.

The worker's dispatcher, lazy launch, readAction boundaries, EDT publication, cancellation and editor release hooks in `GuideRepairExecution` are preserved. `EditorAnalysisExecution` implements the UI-owned `EditorAnalysisRequests` interface, and service lookups use that interface; the execution body does not introduce another worker, dispatcher hop or read action. This adds an interface seam at the UI request boundary, not an extra calculation coroutine. Its exact optimized dispatch cost has not been measured independently.

A concrete additional operation is present in stamp validation. Baseline `AnalysisStamp.matchesCurrent(editor, ...)` calls `matchesCapturedSource` once, then compares tab size, disabled IDs and coverage. Candidate `EditorAnalysisStamp.matchesCurrent(editor, ...)` first compares document stamp and calls model `matchesCapturedSource`, reads tab size when required, and then calls model `matchesCurrent(...)`, which calls `matchesCapturedSource` again. On a successful validation the candidate therefore repeats document-stamp/highlighter/file-type comparisons. It preserves short-circuit rejection before reading tab size, and captures editor identities once; it does not traverse document text, tokenize input or allocate another stamp. The extra helper boundary may also add compiled null checks, but this was not confirmed by bytecode inspection. Whether HotSpot eliminates the repeated operations is unverified.

The new immutable model stamp defensively copies a **nonempty** disabled-language set into a LinkedHashSet/unmodifiable view. Empty sets use `emptySet()` and do not take that allocation branch. `withCoverage` shares the already frozen set. `AnalysisInput` now reads the frozen IDs from the stamp. This is concrete extra capture-time allocation for nonempty configuration; it protects identity consistency from caller mutation and should not be removed blindly. It has not been isolated in these fixture allocation results.

Production `EditorGuideSession` repair request construction now creates a stamp directly instead of a temporary `AnalysisInput`; that removes an input wrapper from this UI path. `GuideRepairRequest` still freezes its own IDs as before. The repair fixture is unchanged and intentionally constructs an `AnalysisInput` itself, so its callback allocation is not a direct measurement of the removed production-session wrapper.

## The +24/+24/+48 byte worker signal

The ordinary/tab production-repair worker allocation statistic rises by +24/+24/+48 bytes across the matched JVM medians. The fixture's `ExecutionThreads` trace surrounds `GuideRepairExecution.calculateGuide` inside `withContext(sample.trace)`. Its request stamp and request object are constructed in the preceding UI callback, outside that traced worker interval, and the fixture passes `emptySet()` for disabled languages. Consequently a newly copied nonempty stamp set, or a request wrapper created in that UI callback, is not a demonstrated cause of these measured worker bytes.

`GuideRepairCalculation` still creates an iterator/sequence, per-line indentation scanners and a guide on successful completion; `calculateGuide` still creates its capture lambdas, prefixes and suspend/read-action machinery. These existing allocation opportunities can have different escape-analysis outcomes after module/class visibility changes. That is a hypothesis, not an identified object accounting for the additional bytes. A 24-byte increment alone does not identify a class or prove a leak. There is no new source-level worker allocation in the inspected path that can safely be removed as a measured regression fix. Causal attribution would require a focused allocation profile identifying the additional object classes and stacks, matched generated-code/JIT inlining or escape-analysis evidence, and counts/timing of successful stamp validations. These are additional diagnostics, not a request to rerun the accepted campaign until its numbers improve.

## Writer and native latency signals

Repeated increases remain real observations of this campaign: nested analysis writer p95, native large-Java/direct/late-traversal writer p95 and maximum read-body p95, plus production repair scheduling and main request-to-observed acceptance. Preserving scheduler/capture source bodies does not make those increases disappear.

The repeated stamp-source comparisons are on a validation path called before/after repair capture and by native consistency checks. This is a concrete source-level candidate for extra hot-path CPU work. It cannot by itself account quantitatively for +26 µs writer p95 or +119 µs native maximum read-body p95 without call counts, JIT behavior and timing attribution. Module linkage/class visibility changes could alter inlining or allocation elimination; scheduler/pump variability and the broad per-JVM analysis distribution also remain plausible contributors. No added lock or thread hop was found in the relevant sources, and no evidence identifies the preserved idle daemon as interference in accepted runs: it was absent in all accepted before/after snapshots. Snapshot absence is not proof of continuous isolation.

## Fix decision

No evidence-backed allocation fix is justified from this source review. Defensive set freezing is an intentional invariant and does not explain this worker interval. Removing read-action or cancellation checks to improve timings would weaken existing semantics and is not justified.

Avoiding duplicate source-identity comparisons is a concrete small optimization opportunity, but its performance benefit and generated-code redundancy are unmeasured. A change must retain cheap stale-source rejection before tab-size lookup and preserve the model/UI boundary. It should be proposed and verified separately, not used to retrospectively call the current candidate performance-equivalent. The duplicate comparisons are introduced bounded constant work, not a proven explanation for writer latency or an allocation root cause. Existing behavior/read-short-circuit tests pass. No production edit was made. The current campaign's repeated timing signals and XML classifier retention limitation remain open in the final report regardless of this source diagnosis.
